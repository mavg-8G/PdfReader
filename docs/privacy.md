# Local document boundary

Folio renders PDFs in process with PDFium, called through the bindings in `PdfReader.Core/PdfiumNative.cs`. There is no browser component, web origin, local server or script engine in the application. PDFium reads the document through a callback over the app's own read-only file handle; no path is handed to the engine.

The PDFium build Folio ships has no JavaScript or XFA support, so code embedded in a PDF is never evaluated. Existing annotations and filled-in form fields are drawn read-only. Clicking a link that points to another page of the same document navigates there; links to web addresses, files and other external targets are ignored. Files dropped onto the window go through the same native validation as the file picker.

The original is held read-only with a Windows sharing mode that prevents concurrent writes. Reads use the source handle without buffering the entire PDF. Save-copy streams to a temporary file beside the destination and replaces the destination only after the copy completes. The original path is rejected. The native save picker asks about replacing an existing destination.

The app stores recent paths, file metadata and view preferences under `%LOCALAPPDATA%\Folio\settings.json`, and the reader's notes, highlights and drawings under `%LOCALAPPDATA%\Folio\Annotations`, one file per document named after a hash of its path. Nothing is written beside or into a PDF. It never stores PDF passwords. Rendered pages, extracted text and search results live only in memory; this is not a secure-erasure guarantee for OS paging, crash dumps or Windows filesystem caches. Clear history removes the app's recent-document list, not the original documents or their annotations. When Folio is installed from its MSIX package, Windows stores this folder with the package and removes it when the app is uninstalled; other ways of running Folio leave it in place. Versions of Folio before the native viewer kept a browser profile in `%LOCALAPPDATA%\Folio\WebView2`; it is no longer used.

There are no app analytics, remote search, cloud sync or document upload services. Windows and a printer selected by the user may have their own network behavior; a network printer receives the print job by the user's explicit print action.

Scanned-page OCR uses the text recognition built into Windows (`Windows.Media.Ocr`) with the recognizer languages installed on the device. Recognition runs only after the user requests it, on one rendered page at a time, and stays on the device. Page images are not kept. Recognized text is held in memory so the page can be selected and searched, and is discarded when the document closes; it is never written to disk. The Windows paging and crash-dump caveats above also apply to OCR memory. Copying selected or recognized text is a user action subject to the system clipboard's own history/sync settings. OCR and copying respect the document's copy restriction.

Production maintenance includes keeping Windows, Windows App SDK and the pinned PDFium package patched, rerunning the included tests after engine updates, signing distributions, and validating representative PDFs and assistive technologies.
